# APP-2 车内独立声浪 App 开发方案

状态：APP-2 本地候选已实现首批运动输入、持续播放和控件；完整车型算法、真机传感器与车内验收仍未完成。目标为 Android 手机固定放在车内，无需电脑或 OBD，依据真实速度、纵向加速度实时合成声浪并切换车型。

## 当前事实与复用选择

- 旧工程已找到：`E:/Tesla_speed/docs/reference/tesla-engine-sound-main`。Compose 仪表、车型选择、音量、BLE/ELM327/CAN 源码可供研究；`app/build.gradle` 未接 externalNativeBuild，Kotlin 未找到 native/loadLibrary 调用，CMake 未接入 JniBridge 所引用的 engine_sim 依赖。该目录的 engine-sim 为空。本次没有构建此参考工程，不能认定为可运行音频 App。
- `prj/android_vehicle_sound_demo/app` 是发送状态给 PC 的 WebSocket 控制器，不在手机合成声音。
- 当前开发工作树中的 `android_vehicle_sound_demo/player` 已有 JNI/Oboe、本地回放、GNSS/IMU、两种实验音色与 C++ runtime。既有任务记录显示构建及主机等价测试通过；APP-2 本次未重跑这些测试。真机播放尚无证据，代码仍未提交。
- 已修复的缺口：旧 PlayerActivity 曾使用 event.values[0] 当纵向加速度，onPause 停止声音且 GPS/IMU 最大年龄统一为 500ms。现在由独立服务持续播放，显式选择车头对应手机轴，重力投影隔离竖向分量，GPS 与 IMU 各自过期，并限制 IMU 速度预测最多偏离最后 GNSS 速度 3m/s。
- 当前 runtime 是合成技术子集，不是完整离线车型算法；不能把两个实验 preset 改名就宣称实现已有车型。

方案比较：①在现有 player 上扩展并参考旧界面（推荐，保留已接通的音频核心）；②修复旧 Compose 工程并移植当前核心（需补齐构建/JNI/状态管理，工作量更大）；③重建 App（重复已有工作，不推荐）。旧参考代码复制前先核实许可证；未核实前只借鉴交互结构，独立实现。

## 输入到声音

GNSS 速度 + 带单调时间戳的 IMU → 姿态及安装方向校准 → 纵向运动估计 → MotionSample → 虚拟挡位/RPM/负载 → 当前 C++ 核心 → Oboe → 手机或用户已连接的车载音频。

速度控制虚拟传动/RPM，加速度参与负载估计；不得把速度简单变成音量，也不得把手机测得的加速度当真实油门。默认手机固定安装；移动手机后重新校准。首版只支持前进声浪，不能由 GPS 速度标量推断倒车。

## 可执行增量

### A. 运动估计，优先实现

- 已修改 `player/PlayerActivity.java` 与 `DriveAudioService.java`，传感器回调留在单一服务线程，运动转换提取到 `MotionEstimator.java`；保留 `MotionInput.java` 和 nativeSubmitMotion 合同，未另建薄封装 `PhoneMotionSource.java`。
- GNSS 提供长期速度基准；IMU 经姿态变换、固定安装纵向校准和偏置/噪声滤波后提供短期动态。静止校准只能估计偏置/重力，不能确定车辆前向；须加入明确安装方向或直线运动校准步骤。
- 分开处理 GPS 与 IMU 新鲜度，保留原始测量时间，不能通过重复发送刷新旧定位。速度精度缺失、无定位、跳点、时间逆序和长时间中断均显式降级。短时预测必须有时限和误差上限，禁止长期积分漂移。
- 已新增 JVM 测试：固定轴投影/侧向分量/竖向轴拒绝、短时速度预测、GPS 超时、异常精度、时间逆序、最大 3m/s IMU 积分偏移、正常重力更新。尚需补实车回放轨迹、停车漂移、长时间无定位恢复和传感器中断边界用例。
- 证据：`:player:testDebugUnitTest` 通过且测试覆盖质量状态转换，状态仅为 SYNTHETIC_PASS。失败则保留 Replay 模式，不启用实车输入默认值。

### B. 持续运行和声音输出

- 新增 `DriveAudioService.java`，将 native 句柄、传感器注册和单一命令生产线程从 Activity 移入服务；Activity 只负责显示/控制。
- 实施前核对目标 Android 版本的前台服务、定位、音频焦点要求。用户在可见界面主动开始，持续通知可停止；锁屏/导航切换继续运行，主动停止释放定位和音频。
- 处理来电/焦点丢失、蓝牙断连、输出设备改变和 Oboe 流错误；蓝牙断开时暂停，避免突然切换到手机大音量播放。恢复需界面明确状态。
- 修改 Manifest、native_player.cpp 与对应资源；实时回调继续禁止分配、锁、文件和 JNI 调用。
- 已验证：模拟器回放音轨开始、前台通知、退到桌面继续运行、点击停止结束；`:player:lintDebug :player:assembleDebug` 通过。服务重建自动化、真机锁屏及蓝牙路由仍待验证。蓝牙端到端延迟单独测量，不能用 native 回调耗时替代。
- 失败处理：停止会话并显示可恢复原因，保留独立 Replay 验证入口。

### C. 驾驶界面和车型算法

- 已提供速度（无效时显示不可用）、输入质量、合成车型选择、总音量、开始/停止、安装方向选择和 Replay 试听。虚拟 RPM/挡位单独显示、正式安装校准向导、旧 DashboardScreen/RpmGauge 的视觉重用尚未完成。
- 先保持当前两个实验 profile 验证输入链路，再盘点 RX-7/Aventador 及 Hellcat、458、LFA、R35、C63、Supra 的当前可用源算法/参数/授权。
- 每个车型独立确定可移植声源层、瞬态状态、滤波/传播成本，复用已有有效参数；完整算法的移动端移植需另列性能预算，不能假定已由 APP-1 覆盖。首批选两款证据最完整且听感差异明确的车型，其余按相同链路扩展。
- 修改 runtime/s12_core、runtime_validation 和 profile 版本合同，逐车型对照 Python 参考导出；保持淡入淡出与相位连续性。
- 验证同轨迹下怠速/加速/收油/换挡、数值等价、实时预算和人工试听。数值通过与车型听感通过分别记录，未通过仍标实验音色。

### D. 真机与交付

- 先单机 Replay 安装启动/切换音色/音量/中断测试，再进行固定安装的真实 GNSS/IMU测试。设备安装沿用明确的设备授权范围，不清除其他 App 数据。
- 至少两款 Android 设备；覆盖 30 分钟持续运行、锁屏、导航切换、无信号、恢复、横竖安装、扬声器及车载蓝牙。记录设备/API、APK SHA、音频路由、xrun、传感器年龄、崩溃及温升表现；道路测试由乘客操作。
- 本地命令（Android 工程目录）：`gradle :app:assembleDebug :player:testDebugUnitTest :player:lintDebug :player:assembleDebug`，使用已配置工具链和 Oboe 本地仓库参数。
- 核心回归（工作树根目录）：`python -m unittest discover -s tools/sound_sim/s12/runtime_validation/tests -v`；新增核心改动还需 native runtime_tests。
- 所有增量通过后提交开发分支并提交既有远端聊天独立审查，保留准确源码 SHA、APK SHA 与设备报告；不将构建成功标成车内验收成功。

## 范围与回退

实施继续使用当前 APP-1 工作树，不覆盖旧参考项目或 Owner 修改。APP-2 源码目前与 APP-1 一并留在功能分支未提交；不可将当前 `EXPERIMENTAL` 合成音色宣传成 RX-7/Aventador/Hellcat 等完整声学算法。模拟器 Debug APK 仅是开发候选。下一步优先完成模型源算法可移植性审计与首批车型设计，再做物理设备验证；两款设备、30 分钟运行、实时 GNSS/IMU、蓝牙路由及人耳试听均未过门。
